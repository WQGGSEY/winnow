## Findings

### 1. [structural] Adapter identity and readiness are conflated

**Components**: `data_adapters.registered`, scoped settings, supervisor envelope bootstrap, `FeasibilityEnvelope`, `data_source_anchor`, `DatasetMaterializer`, `MaterializeResult`, `dataset_manifest`

**Finding**: The system has three incompatible adapter identities and none represents a ready input. A settings entry is keyed by operator ID. The feasibility envelope reduces it to an ID labeled `real_adapter`. The executable registry is keyed by dataset type and never resolves either ID. Production then treats registration and string membership as readiness, while the materializer receipt is too weak to repair that claim after the fact.

**Evidence**: The checked-in adapter has `id`, `kind`, and prose provenance but no source or executable module at `/home/hsj68/research_harness/settings.json:10-16`. Frontend registration creates a different shape with `source` and a fixed module string at `/home/hsj68/research_harness/research_harness/frontend/datasets.py:246-310`. The UI merges entries by ID at `/home/hsj68/research_harness/research_harness/frontend/datasets.py:313-330`, scoped settings replace lists as leaves at `/home/hsj68/research_harness/research_harness/settings_scoped.py:400-446`, and production bypasses both policies by reading project `settings.json` directly at `/home/hsj68/research_harness/research_harness/thread_supervisor.py:324-354`. Bootstrap labels every record with an ID as a real adapter without checking kind, source, or reader. Claim validation then checks ID membership only at `/home/hsj68/research_harness/research_harness/orchestrator/llm_orchestrator/persona_validator.py:794-853`. The executable registry instead uses `raw_data`, `benchmark`, `model_weights`, `factor_set`, `synthetic`, and `custom` at `/home/hsj68/research_harness/research_harness/datasets/registry.py:23-37`. Even its `ok` result does not guarantee a runnable input: `MaterializeResult` permits `materialized_path=None` at `/home/hsj68/research_harness/research_harness/datasets/protocol.py:17-26`, Hugging Face can return that state at `/home/hsj68/research_harness/research_harness/datasets/huggingface.py:85-103`, and the manifest keeps the path nullable with no required digest at `/home/hsj68/research_harness/research_harness/schemas/dataset_manifest.schema.json:20-35`. Local materialization also reuses an existing target without checking source content at `/home/hsj68/research_harness/research_harness/datasets/local_path.py:44-54`.

**Impact**: Different layers disagree about which adapters exist, and production can admit a deployment claim against a declaration that cannot load data. Operator adapters created through the supported UI are invisible to production. A successful receipt may still be unusable or stale, so retries cannot prove which bytes they consumed. A cleaner adapter needs one stable identity, one precedence rule, an explicit probe state, and a receipt that binds that identity to a concrete immutable input.

### 2. [structural] The active path has no typed binding from claim to subprocess

**Components**: Professor experiment design, `ExperimentPlan.inputs`, `JobManifest.inputs`, workspace materialization, `LocalRunner`, runner result

**Finding**: The active path never converts `data_source_anchor` into an experiment input. The existing `inputs` fields are unrestricted transport objects with no parser, delivery rule, or evidence rule. The runner ignores them.

**Evidence**: `Professor.design_experiment()` receives the node and shared-library inventory, then prompts with claim text, baselines, success criteria, and disproof conditions only at `/home/hsj68/research_harness/research_harness/orchestrator/llm_orchestrator/professor.py:230-284`. `_coerce_experiment_plan()` hardcodes empty dataset and snapshot lists at `/home/hsj68/research_harness/research_harness/orchestrator/llm_orchestrator/professor.py:947-956`. Both persisted schemas define `inputs` only as an object at `/home/hsj68/research_harness/research_harness/schemas/experiment_plan.schema.json:77` and `/home/hsj68/research_harness/research_harness/schemas/job_manifest.schema.json:63`. `materialize_experiment_plan()` writes only source files at `/home/hsj68/research_harness/research_harness/orchestrator/experiment_plan.py:683-700`, and `build_job_manifest_from_experiment_plan()` copies inputs unchanged at `/home/hsj68/research_harness/research_harness/orchestrator/experiment_plan.py:703-726`. `LocalRunner.validate_or_raise()` checks no input fields at `/home/hsj68/research_harness/research_harness/runner/local_runner.py:60-76`; `execute()` starts the command with only `cwd=workspace` at `/home/hsj68/research_harness/research_harness/runner/local_runner.py:105-128`; `_runner_result()` records no input receipt at `/home/hsj68/research_harness/research_harness/runner/local_runner.py:190-231`. The MCP coordinator moves directly from plan to manifest to runner without inspecting the node anchor or invoking `research_harness.datasets` at `/home/hsj68/research_harness/research_harness/mcp_server.py:2557-2573`.

**Impact**: Generated source must know an ambient path or environment convention absent from the claim and plan contracts. A node can name one adapter for policy while its code reads another source. Schema-valid plans can still deliver no data, and worker reports cannot attest which dataset backed a result. The existing `inputs` pass-through is a suitable location for a contract, but it is not itself a reusable adapter boundary until it has a typed binding, workspace delivery mechanism, runner validation, and result receipt.

### 3. [structural] Filesystem containment is applied after unsafe paths and code have crossed the boundary

**Components**: refiner dataset specs, local and synthetic materializers, Professor template persistence, `LocalRunner`, ambient data environment

**Finding**: Validation is not concentrated where external paths enter. LLM-authored dataset IDs and source paths reach filesystem joins or code loading before containment. Later workspace checks constrain declared manifest paths, not earlier writes or the running process.

**Evidence**: A `dataset_spec.id` requires only a non-empty string at `/home/hsj68/research_harness/research_harness/schemas/refined_research_plan.schema.json:102-109`. The refiner passes the raw proposed spec to `materialize()` after only filling a missing ID at `/home/hsj68/research_harness/research_harness/agents/research_refiner.py:263-269`. Local and synthetic materializers join that ID directly under the cache root at `/home/hsj68/research_harness/research_harness/datasets/local_path.py:44-46` and `/home/hsj68/research_harness/research_harness/datasets/synthetic.py:60-61`; absolute IDs or `..` segments can escape the cache. Synthetic recipes can load and execute an arbitrary filesystem module in the refiner process at `/home/hsj68/research_harness/research_harness/datasets/synthetic.py:195-213`. On the active path, Professor source paths are joined to template directories and written without `ensure_path_inside()` at `/home/hsj68/research_harness/research_harness/mcp_server.py:2486-2503`. The later plan materializer checks containment only while copying those already-written files into a workspace at `/home/hsj68/research_harness/research_harness/orchestrator/experiment_plan.py:683-700`. `LocalRunner` validates declared workspace, source, and output paths at `/home/hsj68/research_harness/research_harness/runner/local_runner.py:60-103`, but the generated process inherits normal host filesystem access because `subprocess.run()` has no sandbox or sanitized environment at `/home/hsj68/research_harness/research_harness/runner/local_runner.py:119-128`. The current data convention explicitly points generated code to an absolute host directory through `COIN_DATA_DIR` at `/home/hsj68/research_harness/settings.json:176-185` and `/home/hsj68/research_harness/research_harness/mcp_server.py:2463-2471`.

**Impact**: Acquisition and template generation can write outside their intended roots or execute code outside the runner. Once running, experiment code can read or write any path available to the supervisor process regardless of manifest guardrails. Adding a workspace-local input manifest would improve discovery but would not make data access contained or read-only. The architecture must decide whether generated experiments are trusted host code or sandboxed workers, then enforce that choice at the first path and process boundaries.
