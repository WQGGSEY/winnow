## Findings

### 1. [structural] The proposed binding point does not exist on the active connector-forest path

**Severity**: structural

**Finding**: The explanation places adapter binding after `claim_contract.data_source_anchor` has been selected, but a fresh frontend thread does not normally call the claim-design path that selects and validates that anchor. Production calls `seed_forest_from_connector`, which explicitly replaces `design_initial_claim_contract`; the forest builder copies only the four core claim fields and drops both `deploy_grade_scope` and `data_source_anchor`. The proposed seam is therefore attached to the legacy/single-root path rather than the real frontend-to-supervisor lifecycle.

**Evidence**: `research_harness/mcp_server.py:4436-4443` states that connector forest seeding replaces `design_initial_claim_contract`. `research_harness/connector/forest.py:44-58` reconstructs each root contract with only `claim_under_test`, `mandatory_baselines`, `success_criteria`, and `disproof_conditions`. The connector schema permits only those same fields (`research_harness/schemas/connector_session.schema.json:108-123`). Envelope/anchor validation is invoked by `handle_design_initial_claim_contract` (`research_harness/mcp_server.py:2203-2225`) and the revision path, not by `handle_seed_forest_from_connector`; the only call sites are at `research_harness/mcp_server.py:2212` and `research_harness/mcp_server.py:2749`. Meanwhile the authoritative new-thread flow names connector forest seeding as the production entry (`docs/PIPELINE.md:60-65`).

**Impact**: A fresh non-OKX run can seed and execute nodes whose contracts contain no adapter selection, so a binder keyed from the anchor either has nothing to resolve or must invent an implicit choice. Before implementing input delivery, the active forest handoff needs one explicit, envelope-validated scope/anchor assignment step whose result is preserved by child nodes. Otherwise tests around the isolated binder can pass while the genuine frontend acceptance run never exercises it.

### 2. [structural] A directional acceptance run can terminate without proving adapter grounding

**Severity**: structural

**Finding**: The proposed acceptance scope is weaker than the behavior it is intended to certify. `directional` returns from claim-envelope validation before checking the envelope or anchor, and it is the frontend's default supervisor scope. Reaching `accept_with_unverified_screen` therefore proves that the supervisor and publication loop terminated, but it does not prove that a registered real adapter was selected, materialized, delivered, or consumed.

**Evidence**: `validate_claim_fits_envelope` accepts directional claims unconditionally (`research_harness/orchestrator/llm_orchestrator/persona_validator.py:767-771`), whereas only deployment requires an envelope-declared and registered real adapter (`research_harness/orchestrator/llm_orchestrator/persona_validator.py:801-853`). The frontend defaults the supervisor request to `directional` (`research_harness/frontend/server.py:606-615`; `research_harness/frontend/templates/phases/production.html:55-61`). `is_terminal` recognizes a rendered `unverified_screen` independently of runner input evidence (`research_harness/thread_supervisor.py:156-169`). The chosen arXiv file is also already an ambient repository dependency loaded directly by the connector (`research_harness/connector/field_sampler.py:34-49`), while `LocalRunner` launches an unsandboxed subprocess with the workspace merely as `cwd` (`research_harness/runner/local_runner.py:105-128`).

**Impact**: The live acceptance can produce a false positive: publication may complete through the normal supervisor while experiment code omits the adapter manifest or reads the repository file directly. The acceptance thread should use a scope/path that makes the selected real anchor mandatory, and its persisted runner evidence should identify the binding receipt actually consumed. This does not require a positive `goal_achieved` falsifier; it requires adapter use to be a prerequisite for executing the acceptance node.

### 3. [structural] Capability discovery and per-job binding need two lifecycle stages sharing one versioned contract

**Severity**: structural

**Finding**: One post-claim “adapter-binding boundary” is not sufficient because the system makes an availability decision before claim design, then an execution decision after node selection. These stages should share one parsed adapter type and immutable identity, but run at different times: probe/snapshot for the feasibility envelope, then materialize/deliver the already selected snapshot for the job. The explanation currently combines them without defining the versioned contract carried across the boundary.

**Evidence**: The feasibility schema defines `data_sources_available` as what the harness can actually read before any claim is designed (`research_harness/schemas/feasibility_envelope.schema.json:5-30`), but bootstrap stores only adapter ID and provenance and never revisits an existing envelope (`research_harness/thread_supervisor.py:320-354`). Operator entries are mutable by ID and deletable (`research_harness/frontend/datasets.py:301-310,333-360`), while upload already computes a SHA-256 that bootstrap discards (`research_harness/frontend/datasets.py:152-184`). `LocalPathMaterializer` caches by type, ID, and basename and refuses to replace an existing target, with no content fingerprint check (`research_harness/datasets/local_path.py:44-54`), so an updated source can silently resolve to stale bytes. The declaration type is also not an executable dispatch contract: the frontend accepts `real_panel` (`research_harness/frontend/datasets.py:51-53`) but the materializer registry has no `real_panel` handler and rejects unknown types before considering a local source (`research_harness/datasets/registry.py:23-37,59-73`). Finally, both plan and job schemas leave `inputs` as an unconstrained object (`research_harness/schemas/experiment_plan.schema.json:77`; `research_harness/schemas/job_manifest.schema.json:63`), and `runner_result` has no input receipt (`research_harness/runner/local_runner.py:217-231`).

**Impact**: Adapter availability can drift between envelope creation and execution, retries can consume different or stale bytes under the same ID, and every producer/consumer must guess magic `inputs` keys. Evolution to another local dataset, remote materializer, or refreshed snapshot will reopen supervisor, MCP, plan, and runner code independently. The minimal durable design is not a plugin framework: define one small parsed adapter record with an explicit materializer type and source fingerprint; snapshot its probed identity into the thread envelope or adjacent receipt; bind that exact snapshot before the node enters `running`; expose one schema-validated workspace-relative manifest reference to the subprocess; and echo the receipt identity in `runner_result`. The legacy refiner loop and dynamic Python adapter loading remain unnecessary scope.
